## 1 · The problem

TB installed the PWA on his Android phone, sent a test mail from his personal address to his
platform mailbox, and waited: nothing reached the phone, and nothing popped up in the app. The two
mails did reach the bell (rows at 04:57 and 05:33 on staging), so receiving mail and the fan-out
work. In his words: people must see mail "whether in app, out of app, signed out? Anytime. If signed
out they must sign in and it must take them to the exact same mail. If on the app they see a
notification banner (toast), dismissible, that disappears after 3 seconds." He wants the most
robust system possible and the best design on both shells, **now, not in M6**.

What was missing (found 19/10/2026):

- **Push was never built.** `src/services/push/web-push.js` is an empty file, `web-push` is not a
  dependency, there is no VAPID configuration, and `src/jobs/handlers/notification-deliver.js`
  only counts push rows as `push_waiting`.
- **No in-app banner.** The `notification` socket event only reloads the bell's dot
  (`app/src/shell/Bell.tsx`).
- **Mail is only noticed every 2 minutes.** `MAILBOX_IDLE_MAX` defaults to 0 in
  `src/config/env.js` and no `.env` template sets it, so the worker never holds IMAP IDLE.
- **The pane is a generic modal**: All/Unread, an Open button per row, Mark All Read and Done.

What already exists and is reused: `notification`, `notification_preference` and
`push_subscription` tables (`migrations/0060_notifications.sql`), the fan-out with per-category
channels (`src/shared/notifications/fanout.js`, `categories.js`), the delivery job and its queue,
the socket rooms (`src/realtime/socket.js`, `src/services/realtime/emitter.js`), the route map that
derives every link (`src/shared/route-map.js`), the encrypted secret store (`integration_secret`,
`src/services/secrets/encryption.service.js`), the `known_device` cookie, and a sign-in screen that
keeps the URL, so a deep link survives sign-in (`app/src/App.tsx` `Gate`).

### 2.2 Decisions taken in the session and stated to TB (not objected)

- **Soft ask.** Never the browser's cold prompt: a one-time `ShellNotice` per device after
  sign-in, "Turn On" and "Not Now" (Not Now holds 14 days on that device), plus the switch in
  Notification Settings. Safari on an iPhone that has not installed the app shows the Add to Home
  Screen steps first (iOS pushes only to installed web apps, iOS 16.4+).
- **Notification Settings is not a new inventory screen.** It opens from the pane's gear and from
  ⌘K. It holds This Device (status, Turn On or Turn Off, Send Test, Sound in App), Other Devices
  (each removable), and each category's In App, Email and Push switches (Security locked on).
  Settings · Notifications (#74) stays in M6 for the company's reminder rules.
- **Reading.** Opening a notice marks it read; reading a mail conversation marks its notices read;
  a phone notification carries **Mark Read**; the app icon shows the unread count where the
  platform supports `setAppBadge` (desktop, iOS); read system notifications are closed when the
  app next comes to the front.
- **Robust delivery.** `web-push` with TTL, urgency and topic; retries with backoff on 429, 5xx and
  network errors; 404 and 410 revoke the subscription; 401 and 403 (a key mismatch) revoke it so
  the client subscribes again; a delivery log per device (`push_delivery`, unique per notification
  and subscription, so a retry never sends twice); `pushsubscriptionchange` renews through a device
  token; every app start re-syncs the subscription (and re-subscribes when the server key changed).
- **Records.** PROGRESS and MILESTONES say web push and personal preferences were brought forward
  from M6 by TB on 19/10/2026.

### 2.3 What the platforms allow for sound (told to TB)

No browser lets a web page read the ringer, vibrate or silent setting. So:

| Where | Behaviour |
|---|---|
| App closed or in the background (the meeting case) | The phone's own notification: rings, vibrates or stays silent exactly as the phone is set, Do Not Disturb included |
| App open, iPhone (installed) | Chime at 60% through `navigator.audioSession.type = "ambient"`, which the silent switch mutes. iOS has no vibration API |
| App open, desktop | Chime at 60% |
| App open, Android | **Vibrate only** by default (`navigator.vibrate`), because Android cannot tell the page it is on vibrate. A per-device **Sound in App** switch in Notification Settings adds the chime |

## 3 · Architecture

Full design, tables, routes and screens: `docs/guides/notifications.md`. In short:

```
event ─▶ fan-out (rows; channels by category and preference)
      ─▶ notification-deliver job
           in_app ─▶ socket `notification` (bell + banner payload, link only if openable)
           email  ─▶ system mail (unchanged)
           push   ─▶ queue `notification-push`, one job per row, jobId push-<notification_id>,
                     delay 60 s when the person is active somewhere and the category is not security
notification-push job ─▶ skip if read (unless security); active subscriptions of the user;
                         payload (v1); send each; push_delivery row per (notification, subscription);
                         404/410/401/403 revoke; 429/5xx/network retry (BullMQ backoff)
service worker push ─▶ visible client and not iOS and not a test: post to the page (banner, deduped
                       by notification_id), no system notification
                     ─▶ otherwise showNotification: tag per conversation, quiet mode for channel posts
                        (same tag, renotify false), Mark Read action, monochrome badge, avatar icon,
                        app badge count
notificationclick   ─▶ Mark Read: POST with the device token; else focus a window and post `open`,
                       or openWindow(path + n=<id>); sign-in keeps the URL, so it lands on the record
pushsubscriptionchange ─▶ renew through the device token (POST /notifications/push/renew)
```

Payload v1 (under 3 KB): `{ v, id, title, body, path, tag, mode: "alert"|"quiet"|"single",
category, priority, ts, unread, test }`.

Active presence: while the app is visible and touched in the last 5 minutes, the page sends
`presence:active` on its socket every 30 s and `presence:idle` when hidden; the API keeps a Redis
hash `<REDIS_PREFIX>:active:<user_id>` (field: socket id, value: expiry ms, key TTL 75 s). The
worker treats the person as active when any field is in the future.

Device token: on subscribe the server returns a random token once (stored hashed on the
subscription); the page keeps it with the subscription id in IndexedDB (`mycity-push`), where the
service worker reads it for Mark Read and renewal. Those two routes are `anonymous: true` and the
service checks the token in constant time.

## 5 · Repo rules that bite here

- Lists page at 25 through `src/shared/http/paged.js`; no `LIMIT`/`OFFSET` in a repo; a bounded
  read is marked `// pagination:complete <why>` and uses `completeQuery`.
- Every staff route has `requirePermission`, or `self: true` (the caller's own rows), or
  `anonymous: true` (no session; the service checks something else). See `src/http/route.js`.
- One write path: a module's service, in a transaction, with `emit()`; follow-on work in an outbox
  handler. Notification rows are written only by the fan-out.
- Contract first: Zod in `packages/contract`, snake_case, `TABLES` for every schema (gate 6
  `contract-columns`); `schema-drift` checks every SQL string names real columns; never edit
  `contract.gen.ts`.
- Migrations: the milestone's number block, `-- UP` and `-- DOWN`, idempotent, never edit a merged
  one (`docs/MIGRATIONS.md`).
- Frontend: components only from `@mycity/ui` (new ones via `npm run new:component`); tokens only,
  no hex, arbitrary values or inline `style` (F4); sonner only inside the `Toaster` (gate 21);
  a button's handler hands back its promise, never `() => void x()` (F26, lint
  `mycity/no-void-press`); word limits (toast 8, button 3, card title 4, help 35, sentence 20);
  Title Case chrome; no em dashes; Lucide icons through `Icon`.
- Search reaches everything: new actions are findable in ⌘K or carry `search:none <reason>`.
- No donor project names in code (`check/provenance.js`).
- Copy is content when it is the notification's own text (`data-copy="content"`).
